# Технический справочник: Автоматизированный статический анализ банковских ТЗ (SRS/BRD) по стандартам ISO/IEC/IEEE 29148:2018 и IEEE 830-1998

> **Назначение документа:** Машиночитаемая спецификация, база правил, лингвистических паттернов и промпт-архитектура для AI-агента статического аудита требований (Requirements Verification / SRS Auditing) в банковском домене (FinTech). Оптимизировано для загрузки в контекст Claude Code / LLM-пайплайнов.

---

## 1. Архитектура пайплайна статического анализа

Для преодоления ограничений контекстного окна и минимизации галлюцинаций анализ ТЗ выполняется в 4 последовательных этапа:

1. **Ingestion & Structural Parsing (Разбор структуры):** Преобразование Markdown/DOCX/PDF в иерархическое AST-дерево (разделы, таблицы, диаграммы Mermaid/PlantUML, вложенные списки) с присвоением синтетических координат (Anchor IDs).
2. **Atomization & Segmentation (Нарезка):** Выделение атомарных утверждений-требований (Atomic Requirement Units, ARU) и извлечение сущностей (акторы, статусы, лимиты, API-контракты, термины).
3. **Single-Requirement Verification (Локальный аудит по ISO 29148 п. 5.2.5):** Проверка каждого ARU изолированно (с подмешиванием только релевантного контекста из Глоссария) с помощью гибрида детерминированных правил (Regex/NLP) и LLM-судьи.
4. **Cross-Section & Holistic Audit (Глобальный аудит по ISO 29148 п. 5.2.6 / IEEE 830 п. 4.3 и FinTech Domain):** Сверка графа состояний, матриц ролей, глоссария, лимитов и проверка на domain-specific пропуски.

## 2. Формальная декомпозиция свойств единичного требования (ISO/IEC/IEEE 29148:2018, п. 5.2.5)

Каждое атомарное требование (ARU) проверяется по 9 обязательным характеристикам.

### Сводная матрица правил для единичного требования

| ID правила | Свойство (ISO 29148) | Определение для LLM-судьи | Маркеры нарушений (RU) | Ложные срабатывания (False Positives — НЕ считать дефектом) | Severity по умолчанию |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `ISO-525-01` | **Necessary** (Необходимое) | Требование должно описывать обязательную бизнес-потребность, регуляторную норму или системное ограничение, без которого система не выполнит цель. Отсутствие требования создает пробел. | Дублирование одного и того же бизнес-правила в разных разделах разными словами; «золотое покрытие» (gold plating) — фичи, не связанные ни с одной бизнес-целью/User Story. | Уточняющие ссылки на базовые стандарты (например, «в соответствии с 115-ФЗ» или «по стандарту PCI DSS»), если далее раскрывается конкретика. | `MINOR` / `MAJOR` |
| `ISO-525-02` | **Appropriate** (Уместное / Уровень абстракции) | Требование сформулировано на уровне проблемы/поведения («ЧТО система должна делать»), а не преждевременного решения («КАК написать код»), если архитектура не зафиксирована как внешнее ограничение. | Названия конкретных классов/переменных (`if (user.isBlocked == true)`), SQL-запросы вместо бизнес-правил, указание UI-виджетов («использовать красный радиобаттон 12px») в разделе бизнес-логики. | Явные интеграционные контракты (REST/gRPC/ISO 20022), регуляторные алгоритмы (ГОСТ Р 34.10-2012), фиксированные форматы полей (IBAN, БИК, ИНН). | `MAJOR` |
| `ISO-525-03` | **Unambiguous** (Однозначное) | Требование допускает ровно одну интерпретацию всеми участниками (аналитик, разработчик, QA, ИБ). Отсутствуют субъективные оценки, открытые списки и неясные местоимения. | **Слабые модальности:** *по возможности, желательно, рекомендуется, как правило, может, допускается*.<br>**Неизмеримые прилагательные:** *быстро, мгновенно, удобно, интуитивно, надежно, безопасно, корректно, оптимально, гибко*.<br>**Открытые списки:** *и т.д., и т.п., и др., прочие, включая, но не ограничиваясь, например*.<br>**Указательные местоимения без явного антецедента:** *он, она, оно, они, данный, указанный выше, текущий* (когда в предложении $\ge 2$ существительных). | Общепринятые банковские/юридические клише при наличии расшифровки в глоссарии (например, «рабочий день» — если в разделе «Термины» дано строгое определение по производственному календарю ЦБ РФ). | `FATAL` / `MAJOR` |
| `ISO-525-04` | **Complete** (Полное — локально) | Самодостаточность единичного требования: указан **Актор/Триггер**, **Условие**, **Действие**, **Объект** и **Ожидаемый результат** (включая ветку `ELSE` / обработку отказа). | Пассивный залог без актора (*«Заявка переводится в статус Отказ»* — кем? системой автоматически или оператором?); отсутствие альтернативного исхода (*«Если баланс достаточен, списать средства»* — а если недостаточен?). | Ссылки на общую таблицу обработки ошибок (например: *«В случае ошибки валидации вернуть код ошибки согласно Таблице 4.2»*). | `FATAL` / `MAJOR` |
| `ISO-525-05` | **Singular** (Атомарное) | Требование описывает ровно одну проверяемую функцию, одно событие или одно правило валидации. | Соединительные союзы, связывающие разные действия/функции (*«Система должна валидировать ИНН, отправлять запрос в БКИ, рассчитывать скоринговый балл и сохранять лог в Kafka»*); перечисления через `;` внутри одного пункта без подпунктов. | Логически неразрывная атомарная транзакция (например: *«Система должна атомарно списать сумму со счета отправителя и зачислить на счет получателя»*) или составное условие одного действия (`IF A AND B THEN C`). | `MAJOR` |
| `ISO-525-06` | **Feasible** (Реализуемое) | Требование технически, физически и экономически реализуемо в рамках заданных ограничений инфраструктуры, внешних API и законов. | Нереалистичные SLA (*«синхронный ответ от внешнего гос. сервиса СМЭВ за $50\text{ мс}$»*); противоречие законам физики/криптографии (*«расшифровать односторонний SHA-256 хэш пароля»*). | Высоконагруженные требования ($10\,000\text{ RPS}$), если они подтверждены целевой архитектурой и NFR-разделом. | `FATAL` |
| `ISO-525-07` | **Verifiable** (Проверяемое) | Существует конечный, объективный и экономически целесообразный способ проверить выполнение требования тестом (автотестом, нагрузочным стендом, инспекцией). | Отрицательные глобальные кванторы без границ (*«Система никогда не должна падать»*, *«Исключить любые ошибки пользователя»*); отсутствие пороговых значений (*«Система должна выдерживать высокую нагрузку»*). | Качественные требования, сопровождаемые конкретной метрикой приемки (например: *«Удобство интерфейса проверяется успешным прохождением сценария 85% фокус-группы менее чем за $45\text{ с}$»*). | `MAJOR` |
| `ISO-525-08` | **Correct** (Корректное) | Требование точно отражает реальные бизнес-правила, формулы, ставки, регуляторные нормы и не содержит фактических/математических ошибок. | Ошибки в формулах расчета процентов/комиссий, неверная разрядность справочников (например, *«БИК состоит из 10 цифр»* вместо 9), перекрывающиеся диапазоны условий ($0 \le x \le 100$ и $100 \le x \le 500$). | Специфические внутренние правила банка (нестандартные тарифные сетки), если они явно зафиксированы в BRD. | `FATAL` |
| `ISO-525-09` | **Conforming** (Соответствующее шаблону) | Требование оформлено в соответствии с принятым в организации стандартом (EARS — Easy Approach to Requirements Syntax, IEEE 29148 шаблон, наличие уникального ID и обязательных атрибутов). | Отсутствие глагола долженствования (*«должен»* / *«обязан»* — вместо них используется настоящее время *«Система отправляет...»*, которое легко спутать с описанием текущего состояния AS-IS); отсутствие ID требования. | Описательные вводные абзацы (Scope / Context), явно помеченные как информационные (`[INFO]`, `Примечание`). | `MINOR` |

## 3. Свойства набора требований / спецификации целиком (ISO 29148 п. 5.2.6 & IEEE 830 п. 4.3)

Проверка документа как целостной системы проводится на уровне графа сущностей и межсекционных связей.

| ID правила | Свойство | Определение для LLM-судьи | Критерии и паттерны нарушений | Ложные срабатывания (False Positives) | Severity |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `ISO-526-01` | **Complete (Set)** (Полнота набора) | Спецификация описывает реакцию системы на все валидные и невалидные классы входных данных во всех состояниях, включает все интерфейсы, роли и NFR. | Наличие маркеров `TBD/TBR`; наличие роли в матрице доступа без единого сценария использования; описан Happy Path без Negative/Edge сценариев; не описана миграция/обратная совместимость. | Явно вынесенные за рамки релиза пункты в разделе `Out of Scope` (Границы проекта). | `FATAL` |
| `ISO-526-02` | **Consistent** (Непротиворечивость) | Ни одно требование в документе не конфликтует с другим требованием, таблицей, диаграммой или глоссарием. | **Терминологический конфликт:** использование синонимов для одной сущности (*«Клиент»*, *«Пользователь»*, *«Заявитель»*, *«Физлицо»* вперемешку).<br>**Конфликт параметров:** в тексте лимит перевода $100\,000\text{ руб.}$, в таблице тарифов — $150\,000\text{ руб.}$<br>**Временной конфликт:** таймаут сессии $5\text{ мин}$ в разделе ИБ и $15\text{ мин}$ в UX-описании. | Разные значения для разных сегментов/ролей, если это явно обусловлено (например, *«для базового тарифа — $100\,000\text{ руб.}$, для премиального — $500\,000\text{ руб.}$»*). | `FATAL` |
| `ISO-526-03` | **Affordable / Feasible (Set)** (Реализуемость в комплексе) | Совокупность всех функциональных и нефункциональных требований укладывается в бюджет, сроки и архитектурные квоты. | Суммарное время синхронных вызовов цепочки микросервисов ($T_1 + T_2 + T_3 = 4.5\text{ с}$) превышает общий SLA ответа API ($2.0\text{ с}$). | Асинхронная обработка через брокер сообщений (Kafka/RabbitMQ), где клиент получает `202 Accepted` за $200\text{ мс}$, а фоновый процесс идет $5\text{ с}$. | `FATAL` |

| `ISO-526-05` | **Modifiable** (Модифицируемость) | Структура документа позволяет легко изменять требования без каскадных противоречий (отсутствие дублирования констант и правил). | «Хардкод» одного и того же числового параметра (например, ставки НДС или минимальной суммы) в 15 разных абзацах вместо вынесения в единую справочную таблицу параметров. | Повторение названия сущности или ссылки на единый пункт правил (`см. п. 3.2.1`). | `MINOR` |
| `ISO-526-06` | **Traceable** (Трассируемость) | Каждое требование имеет уникальный неизменяемый идентификатор, источник (бизнес-требование/закон) и связано с тестами/архитектурой. | Нумерованные списки Markdown (`1.`, `1.`, `1.`), которые сбиваются при вставке нового пункта; отсутствие маппинга между BRD (бизнес-целями) и SRS (системными требованиями). | Вспомогательные подпункты внутри атомарного требования (например, список полей JSON-объекта внутри одного `REQ-042`). | `MAJOR` |

## 4. Domain-Specific Checklist: Специфика FinTech и банковских ТЗ

При аудите банковских спецификаций LLM-агент обязан проверить наличие и полноту следующих 8 критических доменов. Отсутствие явного описания по любому релевантному пункту классифицируется как `FATAL` или `MAJOR`.

### 4.1. Транзакционность, идемпотентность и распределенные саги
* **Ключ идемпотентности (`Idempotency-Key`):** Определен ли заголовок/поле ключа для всех мутирующих операций (списание, зачисление, создание заявки)? Каков TTL (время жизни) ключа в кэше/БД? Что возвращает система при повторном запросе с тем же ключом (кешированный исходный ответ `200/201` или ошибку `409 Conflict`)?
* **Атомарность и компенсирующие транзакции (Saga Pattern):** При взаимодействии нескольких сервисов (например: *Холдирование в АБС $\rightarrow$ Отправка в СБП $\rightarrow$ Начисление кэшбэка*) описано ли поведение при падении на шаге 2 или 3? Есть ли механизм компенсирующего отката (Refund/Unhold) или очередь гарантированной доставки (Transactional Outbox / DLQ)?
* **Состояние неопределенности (Unknown / Pending):** Что происходит, если от внешнего шлюза (ЦБ, ПЦ, БКИ) получен `Read Timeout` ($504$)? Запрещена ли автоматическая повторная отправка платежа без предварительной сверки статуса (`CheckStatus` / Reconciliation)?

### 4.2. Финансовая математика, валюты и округление
* **Тип данных для денег:** Запрет использования типов с плавающей точкой (`float` / `double`). Требование использования `Decimal` / `Numeric(19,4)` или целочисленного представления в минорных единицах (копейки/центы, `INT64`).
* **Правила округления:** Явно ли задан алгоритм округления на каждом промежуточном и итоговом шаге расчета процентов, комиссий и конвертации?
  * Банковское округление до ближайшего четного (`HALF_EVEN` / округление по Гауссу);
  * Математическое округление (`HALF_UP`);
  * Округление в пользу банка (`CEILING` для комиссий, `FLOOR` для начисления процентов клиенту).
* **Точность расчетов:** Указано ли количество знаков после запятой для промежуточных вычислений (обычно 4–6 знаков, $10^{-4} \dots 10^{-6}$) и для итогового отображения/проводки (2 знака, $10^{-2}$)?
* **Мультивалютность:** Указан ли источник курса (курс ЦБ РФ на дату операции, внутренний курс банка на момент авторизации или клиринга), код валюты по **ISO 4217** (включая нюанс `RUB` vs `RUR` в старых АБС)?

### 4.3. Граничные значения (Boundary Value Analysis) и лимиты
* **Строгие vs нестрогие неравенства:** Проверены ли формулировки «до $100\,000\text{ руб.}$» на неоднозначность ($x < 100\,000$ или $x \le 100\,000$)?
* **Нулевые и отрицательные суммы:** Как система обрабатывает запрос с суммой `0.00` или `-100.00`?
* **Иерархия лимитов:** Описан ли порядок проверки и приоритет лимитов:
  1. Разовый лимит на операцию;
  2. Суточный / месячный лимит по клиенту / карте / счету;
  3. Лимит по уровню идентификации клиента (Упрощенная / Полная по 115-ФЗ);
  4. Регуляторные лимиты (например, лимит СБП без комиссии).
* **Часовой пояс сброса лимитов:** По какому времени сбрасывается «суточный» лимит (UTC, `Europe/Moscow`, локальное время филиала или скользящее окно 24 часа)?

### 4.4. Ролевая модель доступа (RBAC / ABAC) и принцип «четырех глаз»
* **Матрица прав (CRUD + Execute):** Для каждой роли определены права на чтение, создание, редактирование, удаление и подтверждение операций.
* **Принцип разделения полномочий (Maker-Checker / 4-Eyes Principle):** Для критических операций (изменение тарифов, ручное списание, разблокировка по 115-ФЗ, выдача крупного кредита) запрещено ли автору заявки (`Maker`) самому ее утверждать (`Checker`)?
* **IDOR-защита (Insecure Direct Object Reference):** Явно ли прописана проверка принадлежности запрашиваемого счета/карты/договора текущему аутентифицированному `user_id`?

### 4.5. Защита персональных данных (152-ФЗ) и банковской тайны (ст. 26 ФЗ-395-1)
* **Маскирование в UI и API:** Какие поля маскируются при отображении и передаче (PAN карты: `4276 **** **** 1234` по стандарту PCI DSS — не более первых 6 и последних 4 цифр; номер паспорта; телефон)?
* **Запрет логирования ПДн и секретов:** Явно ли запрещено записывать в application-логи (Kibana/ELK/Splunk) CVV/CVC, PIN-блоки, пароли, токены сессий, полные номера карт и биометрические векторы?
* **Сроки хранения и обезличивание:** Указаны ли требования к архивации и удалению данных после отзыва согласия на обработку ПДн (с учетом приоритета 115-ФЗ о хранении данных не менее 5 лет)?

### 4.6. Аудит-логирование (Audit Trail) и непротиворечивость событий
* **Обязательный состав аудит-события:** Фиксируются ли: `timestamp` (с точностью до миллисекунд + таймзона), `actor_id` (пользователь или системный сервис), `ip_address` / `device_fingerprint`, `action_type`, `entity_id`, `old_value` и `new_value` (для изменений), `status` (успех/отказ)?
* **Неизменяемость логов:** Защищены ли аудит-логи от редактирования и удаления даже администраторами БД?

### 4.7. Время, календари и SLA
* **Операционный день банка:** Учитывается ли разница между календарным днем и операционным днем банка (cut-off time, например, платежи после `17:00 МСК` проводятся следующим рабочим днем)?
* **Производственный календарь:** Учтены ли выходные и праздничные дни РФ при расчете сроков просрочки, начисления пеней и сроков рассмотрения заявок?
* **Таймауты интеграций:** Заданы ли отдельно `Connection Timeout` и `Read Timeout` для всех внешних вызовов, а также политика ретраев (Exponential Backoff + Jitter)?

### 4.8. Статусные модели и жизненный цикл сущностей (State Machine)
* **Начальные и терминальные (конечные) состояния:** У каждой сущности (Заявка, Платеж, Договор) есть ровно одно начальное состояние (`CREATED` / `DRAFT`) и явно обозначенные терминальные состояния (`COMPLETED`, `REJECTED`, `CANCELLED`), из которых **нет исходящих переходов**.
* **Изолированные состояния (Dead-ends / Unreachable):** Нет ли статусов, в которые невозможно попасть ни по одному сценарию, или промежуточных статусов, из которых невозможно выйти?
* **Конкурентные переходы (Race Conditions):** Что происходит, если два события приходят одновременно (например, клиент нажимает «Отменить заявку» в ту же миллисекунду, когда скоринг переводит ее в «Одобрено»)? Указана ли оптимистичная блокировка (`version` / `ETag`) или пессимистичная блокировка (`SELECT FOR UPDATE`)?

## 5. Методология проверки таблиц, диаграмм состояний и вложенных списков

### 5.1. Алгоритм верификации графа состояний (Mermaid / PlantUML / Таблицы переходов)
При обнаружении диаграммы состояний (`stateDiagram-v2`) или таблицы переходов агент строит ориентированный граф $G = (V, E)$ и выполняет 5 проверок:

1. **Проверка полноты вершин ($V_{diagram} \equiv V_{text}$):** Сопоставить множество статусов на диаграмме со множеством статусов, упоминаемых в тексте ТЗ и API-контрактах. Любой статус, упомянутый в тексте, но отсутствующий на диаграмме (или наоборот), — дефект `FATAL`.
2. **Поиск висячих вершин (Non-terminal Dead Ends):** Для каждой вершины $v \in V$: если исходящая степень $\text{deg}^+(v) = 0$, проверить, помечен ли статус как терминальный. Если нет (например, статус `WAITING_FOR_SMS` без перехода по таймауту) — дефект `FATAL`.
3. **Поиск недостижимых состояний (Unreachable States):** Для каждой вершины $v \neq v_{start}$: если входящая степень $\text{deg}^-(v) = 0$ — дефект `MAJOR`.
4. **Проверка триггеров и условий (Guards):** На каждом ребре $e = (u \to v)$ должно быть указано:
   * Событие/триггер (кто инициирует переход);
   * Условие перехода (Guard condition);
   * Побочное действие (Side effect, например: отправка Push-уведомления).
5. **Детерминизм переходов:** Если из одного состояния $u$ выходят два ребра по одному и тому же событию, их условия (Guards) должны быть взаимоисключающими.

### 5.2. Алгоритм проверки таблиц (Матрицы ролей, тарифы, маппинг полей)
1. **Полнота ячеек:** Поиск пустых ячеек, прочерков `-` без пояснения в легенде (неясно: «запрещено», «не применимо» или «забыли заполнить»).
2. **Непрерывность диапазонов (Gap & Overlap Analysis):** Для таблиц с числовыми интервалами (суммы, сроки, возраст, скоринговый балл):
   * Проверка на **дыры (Gaps):** например, строка 1: `1 000 – 10 000`, строка 2: `10 001 – 50 000` (куда попадает `10 000.50`?).
   * Проверка на **перекрытия (Overlaps):** строка 1: `до 10 000`, строка 2: `от 10 000` (куда попадает ровно `10 000`?).
3. **Сверка маппинга API:** Проверка соответствия типов данных, обязательности (`Required` / `Optional`) и максимальной длины строк (`maxLength`) между таблицей фронтенда, таблицей бэкенда и контрактом внешней системы (например, фронтенд разрешает 255 символов в поле «Комментарий», а шлюз СБП принимает максимум 140 символов $\rightarrow$ дефект `FATAL`).

## 6. Алгоритмы нарезки (Segmentation) и кросс-секционной сверки (Cross-Section Consistency)

### 6.1. Алгоритм нарезки неструктурированного документа без ID
Когда в документе отсутствуют явные теги `REQ-001`, агент применяет метод **Hierarchical Contextual Chunking**:

1. **Нормализация структуры:** Парсинг заголовков (`H1`–`H6`). Формирование «хлебных крошек» (Breadcrumb path) для каждого абзаца, например: `Раздел 3. Переводы > 3.2. Валидация > Пункт 3.2.4`.
2. **Классификация блоков текста:**
   * `NORMATIVE` (содержит модальные глаголы *должен, обязан, запрещено, требуется*, описания сценариев `Если... то...`, формулы, таблицы правил) $\rightarrow$ подлежит атомизации и проверке.
   * `INFORMATIVE` (введение, цели бизнеса, примеры) $\rightarrow$ используется как контекст, не проверяется на строгий синтаксис EARS.
3. **Декомпозиция сложных списков (List Unrolling):** Если родительский абзац содержит вводную часть (*«Система должна отклонять заявку в следующих случаях:»*), а далее идет маркированный список из 5 пунктов, каждый пункт списка объединяется с родительской шапкой в самостоятельный ARU с присвоением синтетического ID: `SYN-{SectionID}-{ParagraphIndex}-{ItemIndex}` (например, `SYN-3.2-04-02`).

### 6.2. Архитектура кросс-секционной сверки (Entity-Attribute-Value Graph)
Чтобы выявить противоречия в документе объемом $50\text{–}200$ страниц без потери качества в длинном контексте, используется двухпроходный метод **Map-Reduce Entity Extraction**:

* **Шаг 1 (Map — Извлечение фактов):** Из каждого чанка параллельно извлекаются структурированные кортежи (Triples) в формате JSON:
  `{ "entity": "Суточный лимит перевода", "attribute": "max_amount", "value": "100000 RUB", "condition": "Базовый тариф", "source_id": "SYN-2.1-03" }`
  Аналогично извлекаются все термины, роли, статусы, коды ошибок и таймеры.
* **Шаг 2 (Group & Reduce — Кластеризация и сверка):** Все кортежи группируются по нормализованной сущности (`entity` + `attribute`) с помощью эмбеддингов и лемматизации.
* **Шаг 3 (Conflict Detection Prompt):** В LLM-судью передаются только сгруппированные кортежи по одной сущности из разных разделов документа (например, все упоминания «Комиссия за перевод» из разделов 1, 4, 7 и Таблицы 2). Агент проверяет:
  1. Конфликты числовых значений;
  2. Конфликты терминов (один термин означает разное в разных разделах, или разные термины используются для одного объекта);
  3. Несоответствие между функциональными требованиями (FR) и нефункциональными требованиями (NFR).

## 7. Метрики качества и рубрика вердикта «Definition of Ready (DoR)»

### 7.1. Классификация серьезности дефектов (Severity Levels)

| Уровень | Код | Критерии присвоения | Влияние на разработку и тестирование |
| :--- | :--- | :--- | :--- |
| **Критический блокер** | `FATAL` | Прямое противоречие в логике/лимитах; отсутствие обработки ошибок/таймаутов в финансовых транзакциях; уязвимости ИБ/ПДн (логирование секретов, отсутствие IDOR-проверки); невозможность однозначно реализовать расчет денег или переходы статусов; наличие `TBD` в ключевой логике. | Разработка невозможна без остановки и уточнений. Высокий риск финансовых потерь, регуляторных штрафов или критических багов на проде. |
| **Серьезный дефект** | `MAJOR` | Двусмысленные формулировки («быстро», «корректно», «и т.д.»); неатомарные требования (смешение 3+ функций); отсутствие граничных условий (неясно `<` или `<=`); отсутствие аудит-логов; несоответствие между текстом и диаграммой по второстепенным переходам. | Высокий риск расхождения ожиданий бизнеса, разработки и QA. Потребуются переделки на этапе тестирования (Rework). |
| **Редакционное замечание** | `MINOR` | Нарушение шаблона EARS (настоящее время вместо «должен»); отсутствие уникальных ID у пунктов; стилистическая шероховатость при очевидном из контекста смысле; отсутствие приоритизации. | Не блокирует разработку, но усложняет поддержку ТЗ и написание тест-кейсов. |

### 7.2. Формулы расчета индекса качества ТЗ (SRS Quality Score)

Для объективной оценки документа рассчитываются следующие метрики:

1. **Плотность дефектов (Defect Density, $DD$):**
   $$DD = \frac{N_{\text{fatal}} \times 10 + N_{\text{major}} \times 3 + N_{\text{minor}} \times 1}{N_{\text{ARU}}}$$
   где $N_{\text{ARU}}$ — общее количество атомарных требований в документе.

2. **Итоговый балл готовности (Readiness Score, $S_{\text{DoR}} \in [0, 100]$):**
   $$S_{\text{DoR}} = \max\left(0,\; 100 - \left(N_{\text{fatal}} \times 15 + \frac{N_{\text{major}}}{N_{\text{ARU}}} \times 100 + \frac{N_{\text{minor}}}{N_{\text{ARU}}} \times 20\right)\right)$$

3. **Оценка сэкономленных трудозатрат (ROI / Cost of Defect Avoidance):**
   Согласно инженерным бенчмаркам (IBM Systems Sciences Institute / NIST), исправление дефекта требований на этапе кодирования стоит в $5\times\text{–}10\times$ дороже, на этапе системного тестирования — в $15\times$, а в промышленной эксплуатации (FinTech) — в $30\times\text{–}100\times$ дороже, чем на этапе статического анализа ТЗ:
   $$\text{Saved Hours} = N_{\text{fatal}} \times 16\text{ ч} + N_{\text{major}} \times 6\text{ ч} + N_{\text{minor}} \times 1\text{ ч}$$

### 7.3. Матрица принятия решения (Definition of Ready Gate)

* **`REJECTED` (Не готово к разработке — возврат аналитику):**
  * Выполняется **хотя бы одно** условие: $N_{\text{fatal}} \ge 1$ **ИЛИ** $S_{\text{DoR}} < 65$.
  * *Действие:* Передача в разработку заблокирована. Требуется обязательное устранение всех `FATAL` дефектов и повторный аудит.
* **`CONDITIONAL PASS` (Условно готово — допуск с оговорками):**
  * Условия: $N_{\text{fatal}} = 0$ **И** $65 \le S_{\text{DoR}} < 85$.
  * *Действие:* Разработку можно начинать (например, проектирование БД и каркаса сервисов), но аналитик обязан закрыть `MAJOR` дефекты до начала интеграционного тестирования (в рамках текущего спринта).
* **`APPROVED` (Готово к разработке — Definition of Ready пройден):**
  * Условия: $N_{\text{fatal}} = 0$ **И** $S_{\text{DoR}} \ge 85$.
  * *Действие:* ТЗ эталонного качества, передается в разработку и QA без ограничений.

## 9. Системный промпт-шаблон для Claude Code (Инструкция исполнителю)

Ниже приведен готовый блок инструкций, который можно напрямую использовать при запуске аудита файла ТЗ в Claude Code:

```markdown
Ты — Principal Systems Analyst & FinTech QA Lead. Твоя задача — провести глубокий статический аудит технического задания (ТЗ) в соответствии со стандартами ISO/IEC/IEEE 29148:2018, IEEE 830-1998 и правилами из справочника `fintech_srs_auditor_handbook.md`.

### Порядок выполнения:
1. Прочитай целевой файл ТЗ целиком. Если в документе есть диаграммы Mermaid/PlantUML или таблицы — разбери их как формальные графы и матрицы данных.
2. Выполни сегментацию текста на атомарные требования (ARU). Если у пунктов нет явных ID, присвой им синтетические идентификаторы вида `SYN-<Раздел>-<Пункт>`.
3. Проверь каждое ARU по правилам `ISO-525-01` .. `ISO-525-09`, строго отфильтровывая False Positives (не придирайся к корректным банковским терминам и информационным блокам).
4. Выполни глобальную кросс-секционную сверку (`ISO-526-01` .. `ISO-526-07`): сверь глоссарий, лимиты, таймеры, статусы на диаграммах и в тексте, маппинг полей API.
5. Проверь ТЗ по FinTech-чек-листу (идемпотентность, таймауты, округление валют, граничные значения, RBAC, защита ПДн, аудит-логи, терминальные состояния).
6. Рассчитай метрики (`Defect Density`, `Readiness Score`, `Saved Hours`) и вынеси вердикт (`APPROVED`, `CONDITIONAL_PASS` или `REJECTED`).
7. Сформируй отчет:
   - Сначала выведи краткую сводку (Executive Summary) с таблицей метрик и вердиктом.
   - Затем приведи детальный реестр дефектов, отсортированный по критичности (`FATAL` -> `MAJOR` -> `MINOR`), с точными цитатами, кодами правил и готовыми формулировками для исправления (в стиле EARS).
   - В конце сформируй приоритизированный Remediation Plan и приложи полный валидный JSON по схеме `FinTech_SRS_Audit_Report`.
```
